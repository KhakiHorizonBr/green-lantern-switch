## Confirmed facts

- The runtime partitions guest commits into backing slabs no larger than 16 MiB. In arena builds, slabs are carved from the startup arena; the no-arena fallback requests them from `memalign` with 2 MiB alignment. The 35 MiB game request therefore spans multiple backing allocations.
- Logs 021, 022, and 023 fail on the same subsequent 35 MiB backing request with 48 MiB and 32 MiB `STREAMDATA` caps. Log 022 reports 68 MiB free; log 023 reports 70 MiB free, 219 MiB in backing pools, 82 MiB mapped, and Vulkan usage 609/698 MiB with budget available. Log 023's failed aligned allocations from 2 through 16 MiB support aligned-block fragmentation/pressure in the malloc heap.
- 1,536 MiB loader heap caused NVK `VK_ERROR_OUT_OF_HOST_MEMORY` during render-target/upload allocations (log 008). 1,280 MiB reached guest pool initialization but fails on backing; do not raise the heap blindly.
- ReXGlue source sets `SharedMemory::kBufferSize` to exactly 512 MiB. Because sparse residency is unavailable in these logs, Vulkan creates a non-sparse 512 MiB buffer and allocates `VkMemoryRequirements::size` (which may exceed 512 MiB due to alignment). Log 008 reports the fallback but no failure to create/allocate this shared buffer; later OOM messages identify render-target images and 2 MiB upload-buffer allocations. Thus the old log does not support blaming the 512 MiB allocation as the immediate failure.
- Log 008 cannot retrospectively identify exact image-allocation sizes: the NVK message omits request size/caller; ReXGlue logged image dimensions, format, and sample count but not the queried Vulkan requirement size. Added failure diagnostics in the SDK source now record requested/required bytes, alignment, memory-type bits and image details for future runs; rebuild the game before expecting these messages.
- ReXGlue loads a per-app TOML config before initializing NVK. `project/switch/green_lantern.toml.example` documents the existing Switch/NVK runtime controls. ## Arena test: what each result means

- If boot logs an arena reservation and the game completes the 35 MiB backing request, the arena removed the immediate aligned-malloc failure. It does not establish full playability; continue until another guest allocation or gameplay checkpoint fails.
- If startup cannot reserve the arena, the log includes the requested arena size and malloc-free bytes. The 384 MiB contiguous reservation did not fit inside the configured heap at boot; do not change heap size in this run.
- If boot succeeds but the arena logs `exhausted`, the line reports the failing slab size and the largest free arena range. This means current live guest backing exceeded the 384 MiB budget (or, if the largest range is unexpectedly large enough, the arena allocator has a bug to fix).
- If NVK reports `VK_ERROR_OUT_OF_HOST_MEMORY` before the guest reaches the 35 MiB request, the early arena reservation leaves too little system memory available for graphics/runtime allocations. That is a sizing conflict; the heap remains 1,280 MiB and the only project tuning variable in this experiment is the arena size.
