### Guest mapping layout from `rexglue-sdk/src/system/xmemory.cpp`

The tested physical aliases are only four of the nine total mappings. The complete map consists of:

| Guest range | Size | Backing offset | Purpose |
| --- | ---: | ---: | --- |
| `0x00000000–0x3FFFFFFF` | 1 GiB | 0 | Virtual 4 KiB pages |
| `0x40000000–0x7EFFFFFF` | 1008 MiB | `0x40000000` | Virtual 64 KiB pages |
| `0x7F000000–0x7FFFFFFF` | 16 MiB | `0x100000000` | GPU writeback / XPS alias |
| `0x80000000–0x8FFFFFFF` | 256 MiB | `0x80000000` | XEX 64 KiB pages |
| `0x90000000–0x9FFFFFFF` | 256 MiB | `0x80000000` | XEX 4 KiB alias |
| `0xA0000000–0xBFFFFFFF` | 512 MiB | `0x100000000` | Physical 64 KiB alias |
| `0xC0000000–0xDFFFFFFF` | 512 MiB | `0x100000000` | Physical 16 MiB alias |
| `0xE0000000–0xFFFFFFFF` | 512 MiB | `0x100001000` | Physical 4 KiB alias (offset by 4 KiB) |
| `0x100000000–0x11FFFFFFF` | 512 MiB | `0x100000000` | Physical raw alias |

The views describe one sparse 4.5 GiB guest address layout, not 4.5 GiB of RAM. The physical guest heap is 512 MiB; the ordinary virtual and XEX ranges need backing only as pages are committed. Switch shared-memory handles require each mapping size to equal the object size, so a Switch backend must split the backing into aligned chunks, preserve shared identity across aliases, and track page commitment separately. The successful 11-chunk stress run establishes an initial chunk count, but a real allocator still needs virtual/XEX page allocation, guest protection semantics, and capacity tests within the title resource limit.

### Port memory-strategy comparison (2026-10-09)

- Reviewed the available local Project 8 and NFSMW reference trees and the public NFSU2, Simpsons, and Project 8 repositories. NFSU2 has an explicit `RECOMP_NX_SHM=1` mode described as using shared memory for guest RAM instead of code memory. NFSU2 is the original-Xbox/xboxrecomp codebase, so this is a transferable Horizon allocation strategy, not a drop-in ReXGlue/Xbox-360 patch.
- The ReXGlue Xbox-360 ports (Project 8 and Simpsons; the latter says it takes the Switch layer from Project 8) use the ReXGlue guest-memory pattern based on heap backing plus `svcMapProcessCodeMemory`. The active Green Lantern `RexGmCommit` path is the same pattern: `memalign` backing, code-memory shadow, then view mappings. Thus those ports confirm the baseline but do not remove the heap pressure seen in log 012.
- Green Lantern already contains an app-side `SparseGuestPages` shared-memory allocator, but the game target's active commits still enter SDK `RexGmCommit`; the app-side allocator is not wired into that failing path. Its hardware test passed 512 MiB of dynamic shared-memory slabs alongside 512 MiB of physical shared backing (VM probe log 11). This makes the NFSU2 SHM option the strongest lead so far.
- Important integration constraints: Horizon shared-memory mappings are whole-object mappings, while ReXGlue needs page-granular commits across multiple guest views, and the current app allocator tracks XEX mirror pairs but not the full nine-view ReXGlue map. A naive full-slab mapping could expose uncommitted pages and break guard/protection semantics. Before replacing the production allocator, build a small capability test to determine whether shared-memory-backed pages can serve as source backing for the existing code-memory/view mapping path; if not, adapt ReXGlue to map shared slabs safely and preserve commit/decommit behavior.
